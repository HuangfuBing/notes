14.
为什么LLM后训练更偏向Policy-Based RL而不是value-based RL（例如DQN）
1.维度灾难。词表空间太大，传统的动作空间只有十几个离散token；value-based需要为每个action学一个Q(s, a)，a在LLM里很大；
2.奖励稀疏；DQN依赖bootstrapping，Q值估计不准；
3.稳定性不好，PPO有trust region，通过clip机制能保证更新的幅度，避免policy变化太剧烈。
value-based RL要克服的困难太多了，收益又不明确；原则是直接优化policy而不是拐个弯去优化value


15.
GRPO 围绕资源节省
和PPO的不同：
1.优势计算用的是归一化，没有用GAE；
2.KL散度不是放在奖励里而是作为正则项放在目标函数里。

K3估计：
x = pai_{ref} / pai_{theta}
KL[pai_{theta} || pai_{ref}] = x - log(x) - 1
原始KL
log(pai_{theta} / pai_{ref})

K3估计：
1.K3无偏；
2.方差小；
3.非负。

1.原始KL用采样的方式，用样本的均值估计真实的期望，可能出现负值；K3估计不会出现小于0的情况；KL理论上是非负的。
2.K1：无偏估计，方差大，直接计算KL方差很大；K2：1/2 * (logr)^2, r = log(p(x) / q(x))，有偏，方差小，因为有平方保证是正数，计算过程中比K1稳定一些。K3是无偏/方差小

23.
GSPO Qwen3训练过程
解决的问题：
1.GRPO高方差/不稳定
--GRPO对token进行加权，每个token只采样一次，很难校准分布，还会引入方差
2.奖励函数的目标和优化的目标不一致
--reward和optimize一致性的问题；奖励是序列级别的GRPO的优化目标是token级别的；所以要把策略校准，即重要性采样也提到序列级别。

不逐token的做clip，s_i是序列级别的，只对序列加权而不是对序列里面的token加权

GSPO的好处：
1. 训练稳定性好，少数几个坏token不会导致loss太大波动；
2. 消除GRPO对routing replay的依赖。
--GRPO训练时会强制routing replay，记住每一层选哪个专家
--MoE需要考虑routing分布的随机性，要对所有的路由算个期望。
--新旧policy的route结果可能不同，激活不同的专家，导致很多token被clip掉，梯度为0；没有被clip掉的也会引入noise。

MoE训推不一致的原因：
1.引入noise -- 训练的时候会加扰动，推理的时候不会加扰动 -- 鼓励探索更多专家，提升泛化
2.load balance/capacity factor
2.1 训练时加入load balance损失，避免router把大量token都送去少数专家，带来两层不一致。
--优化目标不一致，路由会为了专家均衡作出并非当前token最优的分配，而推理时不需要这个约束。
--训练时有容量限制，每个expert在一个batch中最多接收到一定数量token，后续token可能被丢弃、重新路由等，但是推理时token分布和训练时不同，部署时不做capacity截断，导致很多走备选路径的token进入首选expert。
3.inference engine
--Inference Engine -- rollout
--trainning Engine -- log prob old
--trainning Engine -- log prob new
起三个进程

route replay限制了策略的探索空间；强行replay相当于用一个很大的bias去估计期望；
GSPO优化的是序列，所以对token不敏感

缺点：
1.如果一个训练序列混入一个异常token，就会被丢掉。数据利用率低
2.违背了PPO-clip的初衷，对于一些超出范围的本该被clip的token，只要序列没有超出范围，就会被保留。

on-policy distillation
黑盒蒸馏：sft -- 数据产生、数据本身、回答是离线的
学生强制学习教师的分布

白盒蒸馏：离线蒸馏/在线蒸馏
1.离线蒸馏：
得到teacher的answer的logits，保存（Q，A，logits）；学生本身可以用（Q，A）（hard label）做sft，也可以用logits（soft label）计算KL散度做监督。
L = L_{sft} + alpha * L_{KL}
特点：
1.需要知道模型结构
2.词表要相同
--一半用同类的大模型去蒸小模型

2.在线蒸馏/在线强化蒸馏
解决问题：
1.提供过程监督
--离线蒸馏比较大的问题：死记硬背，答案不是学生做出来的
2.奖励稀疏
--例如PPO，只有最后一个token有reward，其它的都是0；说不出来答案去哪了。

过程：
1.给sft后的学生模型基于prompt采样，根据rollout结果计算出学生模型在logits上的分布（每个token位置上的logits）。
2.对rollout结果，把(Q, A_1, A_2, ... , A_n)送给教师模型，得到每个位置上的dense reward，然后再做PPO/GRPO的强化学习训练。
-- R = -KL(P||Q)，距离越小reward越大
--PPO rollout一条；PPO采样N条

最后的reward是可以把dense reward和RLVR加起来的，效果更好。

KL距离是不对称距离，theta/teacher -- revresed KL； 反之是forward KL

--forward KL：对P_t做的求和/积分，希望学生分布尽可能覆盖教师分布；
---model-covering 都画，神似，不逼真
--reversed KL： mode-seeking 把高概率的狗画得惟妙惟肖，多样性不足。
要从学生模型自己分布里采样数据；学生会学习自己的情况下老师怎么做。黑盒sft是model covering，forward KL；OPD采用reversed KL。

41.
SFT训练到什么程度会考虑RL？

1.为什么先SFT？
--强化学习需要模型能收到足够的正确反馈才行，如果模型输出的东西很难拿到reward，就无法RL
先让模型学到基本的回答格式
2.SFT要训练到什么程度
2.1 训练是否充分：格式是否对齐，是否具有基本的对话能力（例如指令跟随）；性能上有没有达到瓶颈；
2.2 是否有提升空间：pass@k >> pass@1；reward分布是否均匀，既有高分又有低分
2.3 标注成本
3.什么场景下用RL：
3.1 需要引入负反馈纠偏
--SFT是在做fit，只能告诉模型应该做什么，而不是不应该做什么
3.2 任务没有“标准答案”

结论：
SFT更擅长记忆，RL更擅长泛化
--SFT只是在fit这个数据，RL通过策略采样是有助于泛化这个问题的

56.TCOD
将课程学习融入OPD框架
现象:概率坍缩导致的KL散度虚假膨胀
--久而久之学生模型会倾向于生成教师模型一定会生成的高概率token,对于教师模型没见过的token,会被施加极大的KL散度惩罚.教师模型的监督信号不可靠.
来源:compouding errors,学生初期能力比较弱,由于历史是递推的,微小的偏差多轮累积,完整的对话历史在教师概率分布空间的低密度区域,此时教师模型的softmax输出会表现出极高的确定性(分布尖锐,集中在少数几个词上面),此时监督信号失真

TCOD的改善
核心思想:控制学生模型Agent交互的轨迹深度,现在短轨迹上训练,然后逐步暴露在长轨迹中
Forward to Backward:只让学生模型走K步,只计算这K步的KL.K值逐渐增大(这里体现课程学习)
B2F:在训练早期直接让教师模型去生成轨迹,然后学生学习L - k ~ L步.(先让教师模型走90步,先去生成prefix(带到一个中间状态),然后学生在教师生成的prefix上继续生成到结束)
--由于梯度只在学生模型生成的几步计算,优化学生模型的样本来源于学生模型,所以本质还是on-policy

F2B和B2F的区别:核心-阻断误差的累积,让教师模型监督信号可靠
B2F效果优于F2B,开销大

58.
ROPD 如何用闭源大模型做OPD
现有方法依赖于teacher的logits
--将logits依赖换成rubric得分,解决闭源模型logits拿不到的问题

目前来说使用闭源模型做蒸馏的两种方案:
1.数据 + sft;
2.LLM-as-judge; (GPT, Claude充当reward模型,然后做RL)
3.rubric(更加细粒度的评判规则)

ROPD不直接对齐教师的特征分布,而是汇总教师group和学生group,计算多条准则下的得分,加权作为奖励.
Rubricator也是大模型,生成评价准则(细粒度,多维度rubric),这个准则是question-specific的,针对每个question都生成,不是固定的模板;
Verifier也是大模型,对学生模型的生成进行打分,打分出来的reward作为RL的reward.

teacher/students rollouts -> rubricator -> verifier -> reward

落地时存在的问题:
1.rubric非静态
--如果预先写死,泛化性不足;student犯的错误无法预测
2.非Scalar judge,打分粒度要更细
--只打一个分是不够的,综合得分粒度太粗
3.bias校准很难
--verifier评分时如果知道rollout来自教师还是学生,会下意识偏袒教师;如果不去看教师的回复,又会被题目的难度带偏

ROPD具体操作流程
1.Rubric Induction
--对同一个问题,教师/教师模型采多条答案(单教师答案容易把rubric固定到某一种解题路径,多教师答案更容易提取出不同解题路径共享的正确性标准) path_level -> task_level
--把n条student rollout + m条teacher rollout交给rubricator(闭源大模型),生成K条rubric,每条包含标准描述以及所占权重.
2.Rubric-based Verification
--对每个student rollout, verifier逐条判定是否满足这些rubric,计算加权得分,作为该rollout的reward;评判时混合教师轨迹和学生轨迹(盲审),降低bias

multi-teacher保证rubric抽取的是task-level,不是path-level;
sharing保证组内同尺度;
blind保证打分不漂移,减少bias
核心思想:既有区分度,又有可比性

论文中rubricator/verifier/teacher都是一个模型

弊端:
1.成本更高
2.非常依赖prompt设计
3.主要在math/science/medical上表现好,这些客观任务是有标准答案的,没有在主观任务上评测是否有效

Query -> <query, response> -> student

学生模型和教师模型的差别只在prompt,后者看到过答案,可以通过分布Q矫正分布P

稳定SDFT训练的工程技巧:
1.稳定教师训练.
--教师和学生同时更新会导致训练不稳定;教师不动也不行
--EMA,学生模型更新更快,教师模型更新用EMA W_{tea} = alpha * W_{tea} + (1 - alpha) * W_{stu},让高方差的更新更平滑

--上下文学习对模型规模有要求,模型太小不具备上下文学习的能力;theta尽可能大一些
3.可以和RLVR结合训练
--上下文学习的能力更强,越不需要显式的reward辅助
--也可以引入课程学习,前期用reward辅助

66.
MOPD:多教师引导OPD

后训练多场景能力整合到一个大模型的常见方案:
1.Mixed-RL:
pros:
1.只需要训一个模型;
2.通过优化数据配比;
cons:
1.reward的scale.不同领域的reward均值, 方差, 稀疏程度不同.调起来很麻烦;
2.梯度方向可能冲突.多个领域共享一个参数;(see-saw effect)
3.优化的优先级.模型可能会优化简单领域的能力,会影响其它领域的优化.
--看起来loss在降,其实是少数几个领域在降;模型偷懒
4.infra要求不同,统一训练会造成工程的耦合
--不同的任务用到的RL算法, 环境不同; 会提升工程的难度.

2.Cascade RL: 级联的RL
按顺序对多个领域进行训练,例如先做general的sft -> math RL -> code RL -> Agent RL;
--GLM 5, 4阶段RL流水线, 针对不同的能力维度
--overall SFT -> Reasoning RL -> Agentic RL -> General RL -> OPD(弥补出现的灾难性遗忘), 教师模型时Reasoning RL和General RL作为teacher
pros:
1.每个阶段只需要处理一个领域,训练信号相对单纯
cons:
1.后续训练的阶段可能会破坏前一个阶段的能力,即灾难性遗忘;需要做补救,例如GLM收尾时做了OPD
2.训练顺序影响很大
3.误差累积,前一个任务训练的终点不好,影响下一个任务的起点

3.Model Merging 直接在参数空间合并多个专家(task arithmetic)
cons:
1.模型参数要一样
2.不同方向的参数变化会互相抵消, 往往1 + 1 < 2
3.超参数敏感, 每个模型归一化的系数, 专家合并的权重影响很大, 需要做实验定超参

MOPD:多教师引导OPD
SFT -> Domain-Speciallized Training -> MOPD

MODP stage:
根据采样到的样本rollout,把对应的轨迹路由给对应的teacher;
teacher对轨迹做一次prefill,拿到同样上下文里teacher的log p;
计算reverse KL, 拿到即时reward, 套到任何的强化学习框架下做Optimization.

pros:
1.教师和模型同源;
2.实现teacher和student的overlap-ratio(例如top-k token中有几个是一致的), overlap-ratio小的话,教师和学生模型不在一个频道上
--一般overlap-ratio在50% - 70%是比较合适的, 伴随训练过程, o-r会升高;
--衡量整个蒸馏过程的重要依据
cons:
1.领域耦合
--专家的领域之间不是完全独立的. 某个任务可能涉及多个专家的领域
2.跨领域的梯度冲突仍然存在
--作为一个标准的多任务学习, 本质是一个帕累托超平面最优的问题, 任务之间会相互干扰
3.资源, 需要同时加载多个教师模型
--需要做infra优化

OPD在工业界落地实用技巧:
1.教师学生模型的think pattern要合拍;
--不是教师benchmark分高就好
--要看top-k token overlap ratio; 一个成功的OPD overlap ratio不会太低, 而且逐训练步骤升高
2.模型参数大不代表是好老师
--有效的教师往往经过额外的RL/post-training, 具备student没有学过的新策略
--OPD学的是思维模式, OPD有效性在于stu能否提取并学习tea的思维模式
3.OPD也可以冷启动(off-policy cold start)
--stu和tea有gap, 可以先缩小gap, 例如先用teacher生成的轨迹对学生模型做sft, 可提升o-r
4.要用 Teacher-Aligned Prompt **
--使用教师模型特定的输入格式, 遵循教师的prompt template
--如果全用教师的prompt template, 会导致stu的回答太确定, 熵降低, 训练泛化性受损/崩溃, 分布集中在少数token
--trick: 使用教师的prompt, 刻意混入不需要对齐教师格式的OOD prompt
5.KL计算粒度, Token-level vs 全词表?
--各家OPD都是很大分歧
--token-level:多数, 精确的蒙特卡洛近似; GLM-5, Mimo, Qwen3
--全词表:DS-V4, 认为token-level方差大, token-level不稳定
6.Inference-Time Distillation是一个新方向
--在推理过程中识别出决定推理路径走向的关键token(forking token), 遇到关键token时查下教师模型在这些token上的分布
--本质是把OPD信号从训练时延伸到推理时
